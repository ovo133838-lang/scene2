## 2. 数据库与缓存（MySQL 8 + Redis，均为本机，用户指定默认栈）

- MySQL：`root/root@tcp(127.0.0.1:3306)/petshop_t02`，驱动 `go-sql-driver/mysql`（纯 Go），经 go-zero `core/stores/sqlx` 访问；金额 BIGINT 分，时间 DATETIME(UTC)，utf8mb4。
- Redis：`127.0.0.1:6379`，密码 `root`（可配置），经 go-zero `core/stores/redis` 访问。用途（按实际需要，最小化）：
  1. 会话存储：登录 token → 用户身份，TTL 与登录时长一致，服务重启不丢会话也无需 DB 查会话；
  2. 时段余量热点读缓存：列表页余量读 Redis，占位/释放/关闭时写穿并失效，DB 为唯一事实来源（缓存仅加速，不承载业务判断，避免评分口径上的数据不一致）。

完整 MySQL 建表语句见 `apps/petshop/internal/store/schema.sql`（9 张表）。关键约束：

- `bookings` 唯一索引 `(slot_id, pet_id)`——同一宠物同一时段全局唯一（含历史，业务层按有效态判断可否再约）
- `payments.channel_txn` 唯一——同一渠道交易号不得归属两个订单
- `service_records` 唯一 `(booking_id, action)`——核销/开始/完成各只记一次，重复操作天然拒绝
- `refunds` 唯一 `payment_id`——一笔支付最多一条退款单，重试更新 attempt
- `slot_taken(booking_id)` 主键——名额占用行，释放即删，重复关闭幂等

## 3. 并发与幂等设计

| 问题 | 方案 |
| --- | --- |
| 并发抢位超额 | 事务内 `SELECT ... FOR UPDATE` 锁时段行校验余量 + `slot_taken` 占用 + bookings 唯一约束三重保险 |
| 同宠物同时段重复预约 | bookings 唯一索引 + 业务层有效态过滤 |
| 取消 vs 核销并发 | 两操作在同一事务内以 `SELECT status` 为准做条件更新（CAS），后到者返回明确冲突 |
| 重复支付通知 | channel_txn 唯一约束 + 处理结果表幂等判断 |
| 重复关闭释放名额 | slot_taken 主键删除幂等 |
| 重复核销/完成 | service_records 唯一(booking_id, action) |
| 重复退款 | refunds 单条 pending，重试更新 attempt，不新增单 |
| 待付款超时 | 后台 goroutine 每 5s 扫描 pay_deadline 过期者关闭（可配置教学时钟注入） |

## 4. 时间与教学时钟

`internal/clock.Clock` 接口：`Now()`；生产实现读系统时间，测试实现手动推进。待付款 5 分钟、≥2 小时取消线按时钟判断，演示可配置缩短（`--pay-ttl`、`--cancel-window` 启动参数，页面注明）。

## 5. 接口清单（页面 + JSON）

| 方法/路径 | 角色 | 说明 |
| --- | --- | --- |
| POST /login, POST /logout | 全部 | 预置账号登录，签发 HttpOnly 会话 cookie |
| GET / | 按角色 | 重定向到对应工作台 |
| GET /user, POST /user/book, POST /user/pay, POST /user/cancel | user | 预约/发起支付/取消（≥2h 自动、<2h 转审核） |
| POST /api/mock/notify | 渠道 | 支付/退款回调，HMAC-SHA256 验签（密钥环境变量注入） |
| GET /front, POST /front/checkin | reception | 核销（条件：已确认+无待审+本店） |
| POST /staff/start, POST /staff/finish | staff | 服务开始/完成 |
| GET /service, POST /service/review, POST /service/refund-retry, POST /service/anomaly-refund | service | 取消审批、退款重试、异常支付退款 |
| GET /manager, POST /manager/slot, POST /manager/noshow | manager | 建时段、标记未到店、收店核查汇总 |
| GET /health | — | 健康检查 |

越权控制：所有身份取自会话；user 操作校验 booking.user_id；员工操作校验角色与门店归属；渠道回调校验签名。

## 6. 模拟支付渠道（internal/mockchannel）

内置于同进程但独立路径 `/mock/*`（演示页可操作）：受控返回 成功/失败/超时后成功/重复通知；演示时通过页面按钮或 curl 触发，测试用例直接构造通知。渠道与业务共享 DB 仅为演示简化，回调仍走 HTTP + 验签，保证接口真实性。

## 7. 测试策略（对应题面 §1.6）

- 单测：clock/model/store/session/payment（签名）纯逻辑用例。
- 集成：真实 MySQL + 完整 HTTP 栈，31 个场景各执行 2 轮（主链、全部拒绝路径、幂等、并发抢位、退款失败重试、售后投诉）。
- 覆盖率：`-coverpkg` 合并单测与集成，业务包 85.3%；竞态：WSL(Ubuntu) 下 `go test -race ./internal/... ./e2e/` 通过（Windows 无 cgo）。

## 8. 售后服务模块（internal/aftercare）

| 项 | 设计 |
| --- | --- |
| 表 | `complaints(id, booking_id UK, user_id, reason, status, decision_note, created_at, handled_at)` |
| 状态 | `aftercare_pending` → `aftercare_approved` / `aftercare_rejected`（`status VARCHAR(24)`） |
| 提交 | `POST /user/complaint`：事务内 `SELECT ... FOR UPDATE` 校验归属 + 状态必须 completed + 唯一性，再插入 |
| 处理 | `POST /service/complaint`：行锁校验 pending → 写状态与说明；批准后调用 `payment.InitRefund(bookingID)`，复用「退款单唯一 + 可重试」链路 |
| 查询 | 用户页内嵌售后状态列 + 「我的售后服务」区块；客服页「售后服务待处理 / 已处理」两表 |
| 幂等 | 预约级唯一约束 + 退款单按支付单唯一；重复提交/重复处理均返回领域错误 |
| 回调安全 | 退款回调 `POST /api/refund-notify` 增加 `HMAC-SHA256(secret, "refund\|id\|success")` 验签 |
