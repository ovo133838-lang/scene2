# 题目02 需求分析 — 宠物门店的预约、接待、服务与取消退款

依据：`D:/Desktop/Go项目业务场景题.md` 题目02 + 第一部分共同要求。

## 1. 业务背景

宠物护理门店通过 O2O 平台接受洗护预约。店长发布时段，宠物主人预约并支付预约款（9900 分，即服务全款），前台核验到店，服务人员登记开始与完成，客服处理取消与退款。核心矛盾：名额有限且用户操作并发，预约状态、名额占用、收款与退款必须一一对应。

## 2. 角色（预置账号，可信身份）

| 角色 | 账号 | 操作 |
| --- | --- | --- |
| 店长 | `manager` | 创建/查看时段、标记未到店、收店核查汇总 |
| 宠物主人 | `u1`（宠物：豆豆）、`u2`（宠物：毛毛）、`u3`（宠物：雪球） | 预约、付款、取消、查看结果 |
| 前台 | `reception` | 核销到店 |
| 服务人员 | `staff` | 登记服务开始、完成 |
| 客服 | `service` | 审核临近开始取消、跟进退款失败、处理超时后支付异常 |
| 模拟支付渠道 | `POST /api/mock/notify`（渠道回调，带签名） | 支付/退款成功、失败、重复、迟到通知 |

预置：一家门店、一个洗护项目（9900 分）、三个未来时段（每时段 3 个名额）、三个用户与宠物。

## 3. 预约状态机（单一事实来源）

```
PENDING_PAYMENT 待付款(占名额, 5分钟)
  ├─ 付款通知(有效) ──────→ CONFIRMED 已确认
  ├─ 用户主动取消 ────────→ CANCELLED(退款无必要, 名额-1)
  └─ 超时(5min) ──────────→ CLOSED 超时关闭(释放名额, 重复关闭不多释放)
        └─ 迟到支付成功通知 → PAYMENT_ANOMALY 异常支付(不恢复名额)
             └─ 客服发起退款 → 退款流程

CONFIRMED 已确认(占名额, 已收款)
  ├─ 开始前≥2h 取消 → CANCELLED 自动受理, 自动退款
  ├─ 开始前<2h 取消(带原因) → CANCEL_REVIEW 取消待审核(保名额, 不得核销)
  │     ├─ 客服批准 → CANCELLED, 自动退款
  │     └─ 客服拒绝 → CONFIRMED (可正常核销/再次取消)
  ├─ 前台核销 → CHECKED_IN 已核销
  └─ 时段结束仍未到店 → 店长标记 NO_SHOW 未到店(写原因, 不自动退款)

CANCELLED 已取消
  └─ 退款子状态: REFUND_PENDING → REFUND_SUCCESS / REFUND_FAILED(客服重试)
       仅当确实已收款才走退款; 超时关闭未收款的取消无退款

CHECKED_IN 已核销 → IN_SERVICE 服务中 → COMPLETED 已完成
  (三者均不可再走取消退款流程; 核销前提: 本店员工操作、已确认、无待审取消)
```

## 4. 关键业务规则（对照题面逐条）

1. 同一宠物同一时段只能有一个有效预约（待付款/已确认/待审核/已核销/服务中/已完成 均算占用历史判断依据为未取消记录）；名额不足或时段已开始不可预约。
2. 未付款占名额 5 分钟，超时或取消释放；重复关闭不重复释放（幂等）。
3. 支付通知须验签、匹配订单与金额（9900 分）；重复通知只确认一次；同一渠道交易号不得归属两个订单；金额不符/未知订单/验签失败 → 登记并可查询处理结果。
4. 超时关闭后收到的成功支付通知：登记异常支付，不恢复预约与名额；客服核实后发起退款（退给原订单）。
5. 提前 ≥2 小时取消已确认预约：自动受理并全额退款；<2 小时：须填原因，客服批准/拒绝；待审核期间保持名额且不可核销。
6. 取消获准后不可核销；名额只释放一次；退款状态独立可查询；退款失败不能让取消的预约复活。
7. 核销仅限：本店员工 + 已确认 + 无待审取消；核销 → 开始 → 完成 不可逆；重复核销/完成不重复记收入（收入 = 完成服务笔数）。
8. 核销与取消并发：服务端以事务+行锁保证唯一合法结果（先到先得，后到者失败并给出原因）。
9. 时段结束后店长标记未到店并写原因；不自动退款。
10. 收店核查：各时段有效预约、已完成、取消、未到店、退款待处理；已收款/已退款/未退款金额从流水核查，不得把已付款都计作已完成。

## 5. 边界与异常清单

- 并发抢位：N 个请求并发抢最后 1 个名额，恰好 1 个成功。
- 并发取消 vs 核销：仅一种结果成立。
- 重复支付通知、重复退款通知、重复核销、重复关闭：均幂等。
- 金额不符、验签失败、未知订单：记录异常通知，可查询。
- 迟到支付成功：异常支付 + 退款，不影响名额。
- 非本店员工核销、用户操作他人预约：拒绝并记录。
- 时间边界：恰好 2 小时按"≥2 小时"自动受理；待付款恰 5 分钟视为超时。时钟为可配置教学时钟。

## 6. 可验证的验收条件（供验收 Agent 对照）

1. 正常接待全链路可演示并持久化，服务重启后结果可查。
2. 并发 20+ 请求抢 3 名额，最终恰好 3 个成功预约，数据库名额记录一致。
3. 三种取消路径（自动受理 / 批准 / 拒绝）行为与状态机一致，名额只释放一次。
4. 重复支付通知只产生一次确认；迟到支付进入异常列表并退款，名额不变。
5. 取消与核销并发 50 次，最终状态唯一且合法。
6. 退款失败可由客服重试，成功后流水与余额（收款-退款）对得上。
7. 未到店标记需店长权限；店长收店页能区分四类记录并核对金额。
8. 覆盖率 ≥85%，`go vet`、`-race` 通过。

## 9. 售后服务（2026-11-13 追加需求）

顾客诉求：核销并完成服务后若宠物出现不适或对服务不满意，需要能投诉/申请退款，否则没有任何救济渠道。

规则：

| # | 规则 |
| --- | --- |
| S1 | 仅「已完成（completed）」的预约可由下单本人发起售后；核销中/服务中/已取消等状态不可申请 |
| S2 | 每单仅一次售后申请（`complaints.booking_id` 唯一），避免重复退款 |
| S3 | 必须填写原因；客服核实后二选一：**批准**（按原支付单全额原路退款，复用支付域退款单）或**驳回**（必须填写说明，对用户可见） |
| S4 | 批准后生成退款单，退款状态独立可查，失败可在客服页重试；`refunds.payment_id` 唯一，天然保证同一笔支付只退一次 |
| S5 | 售后处理结果与退款进度在用户页、客服页双向可查 |

状态机（售后单）：`aftercare_pending`（待处理）→ `aftercare_approved`（已批准，触发退款）/ `aftercare_rejected`（已驳回），终态不可再次处理。
